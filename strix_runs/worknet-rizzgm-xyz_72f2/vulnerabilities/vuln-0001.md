# IDOR: Cross-account read of client task documents via /api/jobs/{id}/task-file

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-11-10 04:43:15 UTC
**Target:** https://worknet.rizzgm.xyz
**Endpoint:** /api/jobs/{id}/task-file
**Method:** GET
**CWE:** CWE-639
**CVSS:** 4.3
**Confidence:** High
**Fix Effort:** Low

## Description

The `/api/jobs/{id}/task-file` endpoint issues a signed download URL for any job's attached client document to any authenticated user, with no ownership or applicant-relationship check. Any wallet-holder can create an account, enumerate job IDs from the public bootstrap, and download clients' proprietary task documents.

## Evidence

Cross-account request (session 93f615e0…, wallet never applied to job d01fd2a4…):```HTTP/1.1 307 Temporary Redirect
Location: https://eldrxpulpluelgapyfjs.supabase.co/storage/v1/object/sign/deliverables/tasks/797cf372-3c11-435c-b782-f1b18cddea9f/quantum_paper__1_.pdf?token=...
Content-Length: 0```
Signed URL followed:```HTTP/1.1 200 OK
Content-Length: 606561
Content-Type: application/pdf
```
Also issued for job 53ae885e… with session b124c77b… (separate synthetic wallet, no application on that job).

## Impact

Confidentiality of client-supplied task documents is not enforced per-owner. Any authenticated user (or automated agent farm — the platform is explicitly designed for agent participants) can bulk-walk live job IDs and download every client's proprietary task brief, SOP, or internal document. Because agent registration is public and low-friction, this enables systematic scraping of all task-document content on the marketplace within the signed-URL TTL window. Since job metadata (title, brief, acceptanceCriteria, task file name, task path) is already public, the marginal confidentiality loss is restricted to the attached document body itself.

## Counterevidence

Actively looked for scoping: tested task-file with NO cookie (401) versus with an authentication-only session (307, no relationship check). Confirmed response is not cache-poisoning or CF-cache artifact (repeated across separate sessions from separate egress IPs). Confirmed signed URL grants genuine read (200 with 606561 bytes, matching PDF magic bytes). Confirmed endpoint is not applicant-only (the account held no applications on the target jobs). No counter-evidence found hiding the disclosure — neither status-code shaping nor response filtering occurs.

## Confidence Rationale

Confirmed exploitation across more than one unrelated job, distinct unrelated sessions, and both the signed-URL issuance and a full 606KB content download.

## What Would Change This Severity

If the same disclosure pattern exists for `deliverables` (worker submission artifacts) or for the `application` overlay contents, severity would rise. If bucket paths are per-client rather than per-job-UUID, severity may drop further. If llms.txt-described 'Worker Action' is confirmed in product docs as intended public behavior (not a role-scoped pattern), severity would drop to low/informational.

## Technical Analysis

The route handler resolves the session cookie (`arc_worknet_wallet_session`) for authentication, then looks up the job's `taskFilePath` and mints a Supabase Storage signed URL in the `deliverables` bucket. It never checks that (a) the requesting profile is the job's client, (b) the requesting profile has an application on the job, or (c) the job is even visible to the requester beyond its public-read state. Authentication still gates the endpoint (no session → 401), so this is an object-level authorization failure (BOLA/IDOR), not a missing-auth issue. A separate test with no cookie returns 401, and with a valid but unrelated session returns 307 with the signed URL. Snapshot of related design intent: `llms.txt` documents `GET /api/jobs/[id]/task-file` as a "Worker Action" (Section 4.5) — i.e. it is meant to serve the assigned provider, not every authenticated identity.

## Remediation

Server-side, before redirecting: resolve the session's `activeProfileId` and only return the signed URL when (a) the session's profile is the job's `clientProfileId`, OR (b) holds a non-withdrawn application on this job, OR (c) is the assigned provider/evaluator. Return 403 otherwise. Do not rely on the fact that job metadata itself is public — the attachment object is a distinct confidentiality boundary. Also consider lowering the signed-URL TTL from ~1h and naming the bucket path without stable UUIDs.

## Assumptions

Assumes any user can create a session by owning any wallet (verified) and that job IDs are enumerable from public /api/bootstrap (verified: all ~200 live jobs listed). Impact is content confidentiality of client-supplied task attachments; the job's metadata was already public, so the marginal confidentiality loss is the attachment body itself.
