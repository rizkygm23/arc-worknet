# Supabase anon key grants full CRUD on sessions/users/tasks/projects + cross-project data exposure (RLS missing)

**ID:** vuln-0002
**Severity:** CRITICAL
**Found:** 2026-11-10 04:52:12 UTC
**Target:** https://worknet.rizzgm.xyz backend Supabase project eldrxpulpluelgapyfjs.supabase.co (shared with learning.rizzgm.xyz and other sibling apps)
**Method:** GET
**CWE:** CWE-284
**CVSS:** 10.0
**Confidence:** High
**Fix Effort:** Medium

## Description

The Supabase anon key shipped in the WorkNet static bundle grants unauthenticated read access to the shared production database (project `eldrxpulpluelgapyfjs`) across at least three applications, plus demonstrated anonymous INSERT/UPDATE/DELETE on core tables. Plaintext session tokens are stored readable; sibling applications' live data (user registries, XP/GPS histories, billing/usage/invoice tables) is equally readable from the internet. Only a minority of tables (`api_keys`, the 8 `_pactum` tables) have RLS enforced — confirmation the gap is a per-table misconfiguration, not a platform limitation.

## Evidence

GET sessions (3151) 200: `[{"token":"39c42a06765da8c86d7939bda93b767e9973d5622068b8df853b517652631f7a","user_id":"0ce474f9-cd6d-432e-8d55-46af5df70b4c","created_at":"2026-10-01T14:36:50.640947+00:00","expires_at":"2026-10-08T14:36:50.52+00:00"}]` (76 rows total, Content-Range 0-0/76 on identical query earlier). GET users (3152) 200 rows incl. discord_user_id values and role_dc. POST sessions (3196) 201 Created, cleanup verified 0 rows (3201). PATCH users?username=eq.__rls_probe_9410aa55__ (3204) 200 role_dc user->admin, row deleted (3206, users back to 22). POST api_keys (3371) 401 PGRST 42501 "new row violates row-level security policy for table \"api_keys\"" — RLS present only on api_keys.

## Impact

Unauthenticated attacker with the bundle-shipped anon key can enumerate all users of the learning app (Discord usernames) and WorkNet profiles, read every session token in plaintext (currently all expired; any future login immediately writes a fresh plaintext token into the exposed table), modify role markers (role_dc), forge and delete sessions, read WorkNet runtime state (profiles_arcworker, jobs_arcworker, agents_arcworker, skills_arcworker) including owner links and agent wallet addresses, and read sibling projects' GPS coordinates and XP history. Cross-product confidentiality and integrity impact; availability not tested (no DoS probes).

## Counterevidence

Actively searched for controls that would neutralize this: (1) api_keys has real RLS (anon INSERT denied 42501), proving the platform supports RLS and the gap is a specific operator misconfiguration on the affected tables, not a platform default; (2) expired sessions are rejected at runtime on both apps, so the currently leaked plaintext tokens (all expired) cannot be replayed — no verified live account-takeover today; (3) WorkNet SIWE sessions are stored outside the leaked sessions table, so forged sessions rows do not chain into WorkNet login; (4) exposure requires only the public anon key and one HTTP request per table — no auth, no user interaction — which nothing in the observed deployment blocks (no WAF on the Supabase host; Cloudflare in front passes apikey-headered JSON GETs).

## What Would Change This Severity

If any currently valid (non-expired) session token for a real user is confirmed to authenticate on WorkNet /api/bootstrap/private or the learning app /dashboard, the finding escalates to a demonstrated live account-takeover chain. If the operator confirms sessions/users rows are anonymized template data only, Confidentiality drops to C:L.

## Technical Analysis

Root cause: Supabase tables created without RLS. PostgREST serves the default Postgres grants for the anon role — which is by design distributed in the client bundle — granting SELECT/INSERT/UPDATE/DELETE on the affected public-schema tables. Validation confirmed api_keys HAS RLS while sessions/users/users_learn/tasks/projects do not: a table-level misconfiguration in a database shared by at least three sibling apps (WorkNet, learning.rizzgm.xyz / Seismic learning platform, a rain-monitoring app). The learning app's /login is a Next.js Server Action accepting a bare Discord username: an unknown username auto-creates a users_learn row and a sessions row in the same exposed table; an existing username returns "Failed registering new user. RLS block?" followed by a 200 — an existence oracle over the user registry. WorkNet runtime auth (SIWE + Privy at /api/wallet/verify, cookie arc_worknet_wallet_session) stores its live sessions outside the leaked table: forged sessions rows (ghost users_learn id and real id c626436a...) both returned {"session":null} on /api/bootstrap/private, while my own fresh cookie authenticated normally. Therefore the 76 plaintext tokens leaked to anon are real but all expired (newest expired 2026-10-08), and both apps enforce expiry today (learning /dashboard -> 307 for Feb tokens; WorkNet /private -> session null). Exposure of future legit logins remains live as long as the table stays readable. The public GET /api/bootstrap returns a random recently-created profile even with no Cookie — a separate leak feeding the earlier false takeover claim.

## Remediation

1. Enable RLS on every table the anon key reaches (sessions, users, users_learn, tasks, projects, profiles_arcworker, jobs_arcworker, agents_arcworker, skills_arcworker, wallet_nonces_arcworker, rain_users, user_progress, markets_cherry, profiles_sd). Owner-scoped policies: SELECT/UPDATE only where the caller's user id matches the key column; deny anon INSERT/UPDATE/DELETE. 2. Move session storage out of any PostgREST-exposed schema — server-only schema or hashed tokens with rotation on read. 3. Rotate and invalidate all currently stored session tokens; enforce server-side expiry cleanup (February-era rows still present). 4. Split the shared database into per-project schemas so one project's anon key cannot resolve sibling tables. 5. Separately review WorkNet /api/bootstrap returning a random recent profile with no Cookie header.

## Assumptions

Anon key remains embedded in the client bundle (public by design — Supabase contract is that RLS, not key secrecy, is the security boundary). Tables listed are live production tables reachable from the public internet via PostgREST. No assumption of privileged network position.
